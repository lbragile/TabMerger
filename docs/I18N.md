# Internationalization (i18n)

The web app (`packages/web`, [next-intl](https://next-intl.dev), App Router) and the extension
(`packages/extension`, [i18next](https://www.i18next.com) with react-i18next) ship in seven
languages: English, German (`de`), Spanish (`es`), French (`fr`), Japanese (`ja`), Brazilian
Portuguese (`pt-BR`) and Simplified Chinese (`zh-CN`). Every user-facing string comes from a message
catalog, so another language is a translation drop-in. Both apps read the list from
`SUPPORTED_LOCALES` in `@tabmerger/shared`.

## What is translated

Marketing (landing, features, pricing, FAQ, changelog page chrome, contact, share pages, beta guide,
uninstalled survey), the signed-in app (dashboard, account), the error and 404 pages, and page
metadata (titles, descriptions, social-image alt text).

English only, by design:

- **Privacy and Terms.** The binding text is not translated and is not in the catalog. Under another
  locale the page still renders (navbar and footer translated), its content is marked `lang="en"`,
  its canonical is the English URL, and only English is listed as an alternate (sitemap and
  metadata). The ESLint guard skips these files.
- **Release notes** (the entries on `/changelog`) and **known issues** on `/beta`
  (`lib/knownIssues.ts`): historical or frequently edited content. The surrounding page is
  translated.
- **Sign-in pages** (`/auth/*`) live outside `app/[locale]/` and have no prefixed URL. They use the
  default locale.
- Things that are data, not copy: store names, review texts, the share demo's sample tabs, Stripe
  statuses we don't know, messages returned by API routes, and the contact form's subject values
  (sent to the support inbox in English; the visitor sees the translated label).

## How it is wired

| Piece | File |
|---|---|
| Shipped locales, default locale | `SUPPORTED_LOCALES`, `DEFAULT_LOCALE` in `@tabmerger/shared` (`packages/shared/src/constants/locales.ts`) |
| Routable locales, pseudo-locale, RTL list, URL helpers | `packages/web/i18n/locales.ts` |
| next-intl routing (`localePrefix: 'as-needed'`) | `packages/web/i18n/routing.ts` |
| Locale-aware `Link`, `redirect`, `usePathname`, `useRouter` | `packages/web/i18n/navigation.ts` |
| Per-request config (locale + catalog) | `packages/web/i18n/request.ts` |
| Catalog loading, client subset | `packages/web/i18n/messages.ts` |
| Typed keys | `packages/web/global.d.ts` (`AppConfig`) |
| Catalogs | `packages/web/messages/<locale>/<namespace>.json`, listed in `messages/<locale>/index.ts` |

**Routing.** English keeps the existing unprefixed URLs (`/pricing`); other locales get a prefix
(`/es/pricing`). `/en/...` redirects to the unprefixed URL. The routes live under
`app/[locale]/`, and the `[locale]` layout answers 404 for any segment that isn't a routable locale.
The root layout renders `<html lang dir>` from the active locale (`dir` from `RTL_LOCALES`).

**Proxy.** `proxy.ts` runs, in order: the legacy-host redirect, the extension CORS preflight, the
Supabase session refresh and route protection (which strips a locale prefix first, so
`/es/dashboard` is protected too), then the next-intl handler. The handler is skipped for paths
outside `app/[locale]/`: `/api/*`, `/auth/*`, `/firefox-beta/*`, `/sentry-test`, `/sentry-tunnel`,
`/_next/*`, `/_vercel/*`, `robots.txt`, `sitemap.xml`, `llms.txt` and any path ending in a file
extension (icons, Open Graph images, `public/` files). The matcher itself is unchanged: CORS and the
signed-in redirect still need `/api/*` and `/auth/*`. A host-level redirect belongs next to the
legacy-host redirect, at the top.

**Locale detection.** next-intl defaults (`localeDetection: true`): a first unprefixed request is
matched against the `NEXT_LOCALE` cookie, then `Accept-Language`, and redirected to that language's
prefix when it ships. Picking a language in the switcher sets the cookie, and so does next-intl when a
visitor loads a language other than their browser's. The cookie lasts a year (`localeCookie` in
`i18n/routing.ts`, from `LOCALE_COOKIE_ATTRIBUTES` in `i18n/negotiate.ts`; next-intl's default is a
session cookie, which forgot the choice when the browser closed). No `Link` header is sent
(`alternateLinks: false`); hreflang comes from page metadata and the sitemap, which list only public
locales.

**Language switcher.** `LanguageSwitcher` (`components/layout/`) sits beside the theme toggle in the
marketing navbar (from `md`; below that it is a "Language" row in the mobile menu panel) and in the
signed-in app header. It is a button with a languages icon and the current code ("EN"; icon only in
the navbar from `md` to `lg` and in the app header on phones), opening a menu of every public
locale by its own name, the current one checked. It loads its Radix menu code with `next/dynamic`,
like the account menu, and renders nothing while only one locale is public. Choosing a language
writes the `NEXT_LOCALE` cookie (one year, path `/`, SameSite Lax: the same attributes as the
routing config, so the choice survives a browser restart) and then does a full page load of the same path, query string and
hash under the new prefix (`location.replace`). It must not be a client-side `router.replace`: the
root layout owns `<html lang dir>` and the `NextIntlClientProvider`, and a client-side navigation
never re-renders it, so the document kept `lang="en"` and every Client Component kept its English
strings. The cookie has to be written first: with locale detection on, the unprefixed English URL
would otherwise be redirected back to the old language's prefix.

**Client bundle.** Server Components read the full catalog on the server. Client Components get only
the namespaces listed in `CLIENT_NAMESPACES` (`i18n/messages.ts`), serialized into the page; a test
fails if a client file reads a namespace that isn't listed. `global-error.tsx` bundles only
`errors.json`, because it is part of every route's JavaScript.

## Writing translated code

- **Server Component:** `const t = useTranslations('ns')` in a plain function component, or
  `const t = await getTranslations('ns')` in an async one and in `generateMetadata`.
- **Client Component:** `useTranslations('ns')`, and add `'ns'` (or `'ns.sub'`) to
  `CLIENT_NAMESPACES` if it isn't covered yet.
- **Links:** `Link` from `@/i18n/navigation` for pages under `app/[locale]/` (it adds the locale
  prefix). Use `next/link` or `<a>` for `/auth/*`, `/api/*` and other routes outside it.
- **Rich text:** never split a sentence around a link. Put the tag in the message and render it with
  `t.rich`: `"Have more questions? See the <link>FAQ</link>."` with
  `t.rich('key', { link: (chunks) => <Link href="/faq">{chunks}</Link> })`.
- **Counts:** ICU plurals, `{count, plural, one {# tab} other {# tabs}}`. `#` formats the number for
  the locale (1,234); `{count}` inside a branch prints it as is.
- **Numbers, dates, prices:** `useFormatter()` / `getFormatter()`, or `Intl` with the active locale.
  List prices go through `useListPrice()` (`components/pricing/priceFormat.ts`).
- **Metadata:** `pageMetadata({ path, title, description })` (`lib/seo.ts`) adds the localized
  canonical, hreflang alternates, `og:locale` and the translated social-image alt text.
- **AI copy:** keep the `NEXT_PUBLIC_AI_ENABLED` branch in the code and give each branch its own
  message (`faq.ai.answer` / `faq.ai.answerComingSoon`).

### Adding a key

1. Add it to the right file in `packages/web/messages/en/` (one file per page or feature area; a
   new namespace also needs a line in `messages/en/index.ts`).
2. Use it: `t('key')`. A missing or misspelled key fails `pnpm --filter @tabmerger/web type-check`.
3. In a Client Component, make sure its namespace is in `CLIENT_NAMESPACES`.

Messages are ICU MessageFormat: a literal `{`, `}`, `<` or `>` must be quoted (`'<'group'>'`).

### Guards

- `pnpm --filter @tabmerger/web lint` fails on literal words in JSX (`react/jsx-no-literals`) and on
  English in `aria-label`, `title`, `alt`, `placeholder` and `aria-roledescription` in the
  translated files. Punctuation, symbols and brand names are allow-listed in
  `packages/web/eslint.config.js`. The rule does not see strings inside ternaries or variables
  (`{open ? 'Hide' : 'Show'}`), so review those by hand.
- `__tests__/i18n-catalogs.test.ts` checks every locale folder against English: same keys, same
  placeholders, same rich-text tags, and that every English message parses.
- `__tests__/i18n-infrastructure.test.tsx` checks the client namespace list, the locale helpers,
  and that the English plan features, plan names and prices read exactly like `PRICING_TIERS` and
  `formatListPrice` in `@tabmerger/shared`.

## Adding a language

1. **Catalog:** copy `packages/web/messages/en/` to `packages/web/messages/<locale>/` (BCP 47 tag,
   e.g. `es`, `pt-BR`) and translate the JSON values. Keep keys, `{placeholders}` and `<tags>`. A
   missing key falls back to English at runtime, but the catalog test fails until it is there.
2. **Loader:** add the locale to `CATALOGS` in `packages/web/i18n/messages.ts`
   (`es: async () => (await import('@/messages/es')).default`).
3. **Routing:** add the locale to `SUPPORTED_LOCALES` in `packages/shared/src/constants/locales.ts`.
   That alone makes it routable at `/<locale>/…`, lists it in hreflang and the sitemap, and shows the
   language switcher (in the site header). Add its native name to `LOCALE_NATIVE_NAMES` and its
   `og:locale` to `OG_LOCALES` (`packages/web/i18n/locales.ts`); for a right-to-left language, add it
   to `RTL_LOCALES` and do the RTL work below first.
4. **Sitemap:** nothing to do (`app/sitemap.ts` lists every public locale; Privacy and Terms stay
   English-only). Check `/sitemap.xml` shows the new URLs.
5. **Tests:** `pnpm --filter @tabmerger/web test` (the catalog test picks the new folder up) and
   update `PUBLIC_LOCALES` expectations in `i18n-infrastructure.test.tsx` and the hreflang
   expectations in `seo-metadata.test.tsx` / `sitemap-robots.test.ts`.
6. Check the pages in the browser at `/<locale>/…`, including the dashboard.

## Pseudo-locale (`en-XA`)

In `next dev` and in tests, `/en-XA/...` serves an accented copy of English, about 35-40% longer and
wrapped in `[ ]`, generated from the English catalog at load time (`i18n/pseudo.ts`). Use it to find
text that overflows, is cut off, or is not translated (anything without accents). It is not in the
locale list of a production build (`next build` sets `NODE_ENV=production`), so it is never
reachable on a deployment, and it is never in hreflang, the sitemap or the language switcher.

## Right-to-left: work to do before shipping an RTL language

`dir` already follows the locale. The CSS still uses physical directions in places that matter for
layout; convert these to logical properties (`ms-`/`me-`/`ps-`/`pe-`, `start-`/`end-`,
`text-start`) when the first RTL language is added:

- `components/layout/Navbar.tsx`: `mr-4`, `lg:mr-8` on the logo and nav block; `space-x-2` on the
  right cluster.
- `components/layout/MobileNavToggle.tsx`: `ml-auto` on the star count; the `absolute inset-x-0`
  panel is fine.
- `components/marketing/Hero.tsx`: `lg:ml-auto` on the copy column.
- `components/marketing/PricingTeaser.tsx`, `components/pricing/PricingCard.tsx`: `ml-1` on the
  period, `text-left` defaults.
- `components/marketing/ReviewCard.tsx`, `ReviewsCarousel.tsx`: `ml-auto`, `pl-1.5`, the `left-3` /
  `right-3` arrows, and the carousel's `translate3d` direction.
- `components/dashboard/GroupGrid.tsx`: `border-left` accent, `right-2` select box, `ml-auto`,
  `pl-6`, `left-1/2 -translate-x-1/2` floating bar.
- `components/dashboard/SessionCard.tsx`, `BackupsSection.tsx`: `-ml-2`, `pl-4`.
- `components/errors/ErrorPageShell.tsx`: `right-1`/`sm:-right-8` and the rotated floating tab.
- `components/uninstall/UninstallSurveyForm.tsx`: `-left-[625rem]` honeypot, `text-right` counter.
- `app/[locale]/(marketing)/beta/page.tsx`: `pl-5` lists, `border-l-2 pl-4` known issues,
  `list-inside` numbering.
- Icons that point a direction (`ArrowRight`, `→` in copy, chevrons) need mirroring.

## Extension

The popup, the extension pages and the background script (right-click menu, notifications, badge
titles) are translated. The store listing and the manifest `name`/`description` stay English (no
`_locales/`).

| Piece | File |
|---|---|
| Setup, `resolveLocale`, `t` for non-React code | `packages/extension/src/lib/i18n.ts` |
| Catalog registry | `packages/extension/src/locales/index.ts` |
| Catalogs | `packages/extension/src/locales/<locale>/<area>.json`, listed in `<locale>/index.ts` |
| Typed keys (from English) | `packages/extension/src/i18next.d.ts` |
| Catalog checks | `packages/extension/src/locales/validate.ts`, `src/__tests__/unit/locales/catalogs.test.ts` |
| Pseudo-locale (dev builds, `build:dev:pseudo`) | `packages/extension/src/lib/pseudoLocale.ts` |

**Language.** The one picked in the popup header's language menu (applied at once) or in
Settings → General → Language (applied with "Save changes"); both show each language by its own
name (`LOCALE_NATIVE_NAMES` in `@tabmerger/shared`, which the web switcher uses too). "Browser
default", the default, is the browser's UI language (`chrome.i18n.getUILanguage()`), narrowed to a
shipped catalog: the exact tag, else its language (`de-AT` → `de`), else a shipped region of that
language (`pt-PT` → `pt-BR`, `zh-SG` → `zh-CN`), else English. Traditional Chinese (`zh-TW`,
`zh-HK`, `zh-MO`, `zh-Hant`) gets English, not Simplified. A key missing from a catalog shows
English.

The choice is per device and never synced (`src/lib/localePreference.ts`). It is stored twice:
in the extension origin's `localStorage` (`tabmerger-locale`), which extension pages read
synchronously so i18next starts in the right language with no flash, and in `chrome.storage.local`
(`tm_locale`) for the background worker, which has no `localStorage`. The worker applies the stored
choice on start, follows `storage.onChanged` and rebuilds the right-click menu; handlers that can
wake it (reminder notifications, sync-now replies, a new "Quick Save" group) wait for that first
read. Open extension pages follow the change too. Every stored value is validated with
`isSupportedLocale` and falls back to "Browser default". A change calls `i18n.changeLanguage` and
`applyDocumentLocale`, so `<html lang dir>`, dates, numbers and plurals follow.

**Writing translated code.** `const { t } = useTranslation()` in components and `<Trans>` for a
sentence with markup; `t` from `@/lib/i18n` in hooks and the background script. Interpolation is
i18next's `{{name}}`, not ICU. Counts use `t('common.tabCount', { count })`, which picks
`tabCount_one` / `tabCount_other` with `Intl.PluralRules`. Each language has its own plural forms:
Japanese and Chinese have only `_other`, Spanish, French and Portuguese add `_many`. The catalog
test checks every locale has exactly its language's forms, and the same keys, `{{placeholders}}`
and tags as English.

**Adding a language.** Copy `src/locales/en/` to `src/locales/<locale>/`, translate the values (and
adjust the plural keys to the language's forms), add the folder to `catalogs` in
`src/locales/index.ts`, then add the locale to `SUPPORTED_LOCALES`. That list is shared, so the web
catalog must be complete first.
