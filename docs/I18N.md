# Internationalization (i18n)

The web app (`packages/web`, [next-intl](https://next-intl.dev), App Router) and the extension
(`packages/extension`, [i18next](https://www.i18next.com) with react-i18next) ship in eighteen
languages: English, German (`de`), Spanish (`es`), French (`fr`), Italian (`it`), Russian (`ru`),
Korean (`ko`), Turkish (`tr`), Indonesian (`id`), Polish (`pl`), Vietnamese (`vi`), Hindi (`hi`),
Japanese (`ja`), Brazilian Portuguese (`pt-BR`), Simplified Chinese (`zh-CN`), and the right-to-left
Arabic (`ar`), Hebrew (`he`) and Persian (`fa`) (see "Right-to-left"). Every user-facing string comes from a message
catalog, so another language is a translation drop-in. Both apps read the list from
`SUPPORTED_LOCALES` in `@tabmerger/shared`.

## What is translated

Marketing (landing, features, pricing, FAQ, changelog page chrome, contact, share pages, beta guide,
uninstalled survey), the signed-in app (dashboard, account), the error and 404 pages, and page
metadata (titles, descriptions, social-image alt text).

English only, by design:

- **Privacy and Terms.** The binding text is not translated and is not in the catalog. Under another
  locale the page still renders (navbar and footer translated), its content is marked `lang="en"`,
  its canonical is the English URL, and only English is listed as an alternate (sitemap and
  metadata). The ESLint guard skips these files.
- **Release notes** (the entries on `/changelog`) and **known issues** on `/beta`
  (`lib/knownIssues.ts`): historical or frequently edited content. The surrounding page is
  translated.
- **Sign-in pages** (`/auth/*`) live outside `app/[locale]/` and have no prefixed URL. They use the
  default locale.
- Things that are data, not copy: store names, review texts, the share demo's sample tabs, Stripe
  statuses we don't know, messages returned by API routes, and the contact form's subject values
  (sent to the support inbox in English; the visitor sees the translated label).

## How it is wired

| Piece | File |
|---|---|
| Shipped locales, default locale | `SUPPORTED_LOCALES`, `DEFAULT_LOCALE` in `@tabmerger/shared` (`packages/shared/src/constants/locales.ts`) |
| Routable locales, pseudo-locale, RTL list, URL helpers | `packages/web/i18n/locales.ts` |
| next-intl routing (`localePrefix: 'as-needed'`) | `packages/web/i18n/routing.ts` |
| Locale-aware `Link`, `redirect`, `usePathname`, `useRouter` | `packages/web/i18n/navigation.ts` |
| Per-request config (locale + catalog) | `packages/web/i18n/request.ts` |
| Catalog loading, client subset | `packages/web/i18n/messages.ts` |
| Typed keys | `packages/web/global.d.ts` (`AppConfig`) |
| Catalogs | `packages/web/messages/<locale>/<namespace>.json`, listed in `messages/<locale>/index.ts` |

**Routing.** English keeps the existing unprefixed URLs (`/pricing`); other locales get a prefix
(`/es/pricing`). `/en/...` redirects to the unprefixed URL. The routes live under
`app/[locale]/`, and the `[locale]` layout answers 404 for any segment that isn't a routable locale.
The root layout renders `<html lang dir>` from the active locale (`dir` from `RTL_LOCALES`).

**Proxy.** `proxy.ts` runs, in order: the legacy-host redirect, the extension CORS preflight, the
Supabase session refresh and route protection (which strips a locale prefix first, so
`/es/dashboard` is protected too), then the next-intl handler. The handler is skipped for paths
outside `app/[locale]/`: `/api/*`, `/auth/*`, `/firefox-beta/*`, `/sentry-test`, `/sentry-tunnel`,
`/_next/*`, `/_vercel/*`, `robots.txt`, `sitemap.xml`, `llms.txt` and any path ending in a file
extension (icons, Open Graph images, `public/` files). The matcher itself is unchanged: CORS and the
signed-in redirect still need `/api/*` and `/auth/*`. A host-level redirect belongs next to the
legacy-host redirect, at the top.

**Locale detection.** next-intl defaults (`localeDetection: true`): a first unprefixed request is
matched against the `NEXT_LOCALE` cookie, then `Accept-Language`, and redirected to that language's
prefix when it ships. Picking a language in the switcher sets the cookie, and so does next-intl when a
visitor loads a language other than their browser's. The cookie lasts a year (`localeCookie` in
`i18n/routing.ts`, from `LOCALE_COOKIE_ATTRIBUTES` in `i18n/negotiate.ts`; next-intl's default is a
session cookie, which forgot the choice when the browser closed). No `Link` header is sent
(`alternateLinks: false`); hreflang comes from page metadata and the sitemap, which list only public
locales.

**Language switcher.** `LanguageSwitcher` (`components/layout/`) sits beside the theme toggle in the
marketing navbar (from `md`; below that it is a "Language" row in the mobile menu panel) and in the
signed-in app header. It is a button with a languages icon and the current code ("EN"; icon only in
the navbar from `md` to `lg` and in the app header on phones), opening a menu of every public
locale by its own name, the current one checked. It loads its Radix menu code with `next/dynamic`,
like the account menu, and renders nothing while only one locale is public. Choosing a language
writes the `NEXT_LOCALE` cookie (one year, path `/`, SameSite Lax: the same attributes as the
routing config, so the choice survives a browser restart) and then does a full page load of the same path, query string and
hash under the new prefix (`location.replace`). It must not be a client-side `router.replace`: the
root layout owns `<html lang dir>` and the `NextIntlClientProvider`, and a client-side navigation
never re-renders it, so the document kept `lang="en"` and every Client Component kept its English
strings. The cookie has to be written first: with locale detection on, the unprefixed English URL
would otherwise be redirected back to the old language's prefix.

**Client bundle.** Server Components read the full catalog on the server. Client Components get only
the namespaces listed in `CLIENT_NAMESPACES` (`i18n/messages.ts`), serialized into the page; a test
fails if a client file reads a namespace that isn't listed. `global-error.tsx` bundles only
`errors.json`, because it is part of every route's JavaScript.

## Writing translated code

- **Server Component:** `const t = useTranslations('ns')` in a plain function component, or
  `const t = await getTranslations('ns')` in an async one and in `generateMetadata`.
- **Client Component:** `useTranslations('ns')`, and add `'ns'` (or `'ns.sub'`) to
  `CLIENT_NAMESPACES` if it isn't covered yet.
- **Links:** `Link` from `@/i18n/navigation` for pages under `app/[locale]/` (it adds the locale
  prefix). Use `next/link` or `<a>` for `/auth/*`, `/api/*` and other routes outside it.
- **Rich text:** never split a sentence around a link. Put the tag in the message and render it with
  `t.rich`: `"Have more questions? See the <link>FAQ</link>."` with
  `t.rich('key', { link: (chunks) => <Link href="/faq">{chunks}</Link> })`.
- **Counts:** ICU plurals, `{count, plural, one {# tab} other {# tabs}}`. `#` formats the number for
  the locale (1,234); `{count}` inside a branch prints it as is.
- **Numbers, dates, prices:** `useFormatter()` / `getFormatter()`, or `Intl` with the active locale.
  List prices go through `useListPrice()` (`components/pricing/priceFormat.ts`).
- **Metadata:** `pageMetadata({ path, title, description })` (`lib/seo.ts`) adds the localized
  canonical, hreflang alternates, `og:locale` and the translated social-image alt text.
- **AI copy:** keep the `NEXT_PUBLIC_AI_ENABLED` branch in the code and give each branch its own
  message (`faq.ai.answer` / `faq.ai.answerComingSoon`).

### Adding a key

1. Add it to the right file in `packages/web/messages/en/` (one file per page or feature area; a
   new namespace also needs a line in `messages/en/index.ts`).
2. Use it: `t('key')`. A missing or misspelled key fails `pnpm --filter @tabmerger/web type-check`.
3. In a Client Component, make sure its namespace is in `CLIENT_NAMESPACES`.

Messages are ICU MessageFormat: a literal `{`, `}`, `<` or `>` must be quoted (`'<'group'>'`).

### Guards

- `pnpm --filter @tabmerger/web lint` fails on literal words in JSX (`react/jsx-no-literals`) and on
  English in `aria-label`, `title`, `alt`, `placeholder` and `aria-roledescription` in the
  translated files. Punctuation, symbols and brand names are allow-listed in
  `packages/web/eslint.config.js`. The rule does not see strings inside ternaries or variables
  (`{open ? 'Hide' : 'Show'}`), so review those by hand.
- `__tests__/i18n-catalogs.test.ts` checks every locale folder against English: same keys, same
  placeholders, same rich-text tags, and that every English message parses.
- `__tests__/i18n-infrastructure.test.tsx` checks the client namespace list, the locale helpers,
  and that the English plan features, plan names and prices read exactly like `PRICING_TIERS` and
  `formatListPrice` in `@tabmerger/shared`.

## Adding a language

1. **Catalog:** copy `packages/web/messages/en/` to `packages/web/messages/<locale>/` (BCP 47 tag,
   e.g. `es`, `pt-BR`) and translate the JSON values. Keep keys, `{placeholders}` and `<tags>`. A
   missing key falls back to English at runtime, but the catalog test fails until it is there.
2. **Loader:** add the locale to `CATALOGS` in `packages/web/i18n/messages.ts`
   (`es: async () => (await import('@/messages/es')).default`).
3. **Routing:** add the locale to `SUPPORTED_LOCALES` in `packages/shared/src/constants/locales.ts`.
   That alone makes it routable at `/<locale>/…`, lists it in hreflang and the sitemap, and shows the
   language switcher (in the site header). Add its native name to `LOCALE_NATIVE_NAMES` and its
   `og:locale` to `OG_LOCALES` (`packages/web/i18n/locales.ts`); for a right-to-left language, add it
   to `RTL_LOCALES` (`packages/shared/src/constants/locales.ts`) and, if Geist lacks its script, give it a script font (see "Right-to-left").
4. **Sitemap:** nothing to do (`app/sitemap.ts` lists every public locale; Privacy and Terms stay
   English-only). Check `/sitemap.xml` shows the new URLs.
5. **Tests:** `pnpm --filter @tabmerger/web test` (the catalog test picks the new folder up) and
   update `PUBLIC_LOCALES` expectations in `i18n-infrastructure.test.tsx` and the hreflang
   expectations in `seo-metadata.test.tsx` / `sitemap-robots.test.ts`.
6. Check the pages in the browser at `/<locale>/…`, including the dashboard.

## Pseudo-locale (`en-XA`)

In `next dev` and in tests, `/en-XA/...` serves an accented copy of English, about 35-40% longer and
wrapped in `[ ]`, generated from the English catalog at load time (`i18n/pseudo.ts`). Use it to find
text that overflows, is cut off, or is not translated (anything without accents). It is not in the
locale list of a production build (`next build` sets `NODE_ENV=production`), so it is never
reachable on a deployment, and it is never in hreflang, the sitemap or the language switcher.

## Right-to-left

Arabic, Hebrew and Persian are right-to-left (`RTL_LOCALES` and `isRtlLocale` in
`packages/shared/src/constants/locales.ts`, shared with the extension; `packages/web/i18n/locales.ts`
re-exports the list).
The root layout sets `<html dir>` from `localeDirection(locale)`, and everything else follows
from that one value. The rules for the web app:

**Logical CSS only.** Write `ms-`/`me-`, `ps-`/`pe-`, `inset-s-`/`inset-e-` (Tailwind v4.2+; the
older `start-`/`end-` still work but are deprecated), `text-start`/`text-end`, `border-s`/`border-e`,
`rounded-s`/`rounded-e`, and `borderInlineStart`-style properties in inline styles, never `ml-`,
`pr-`, `left-`, `text-left`, `border-l` or `borderLeft`. `space-x-*` is fine: v4 builds it from
`margin-inline-*`. `ltr:`/`rtl:` variants are for what has no logical form: a translate
(`rtl:data-[state=checked]:-translate-x-5` on the switch thumb), a rotation, a gradient direction
(the group card sets `--accent-to` with `rtl:`), or a physical side that has to pair with a
physical value (the cookie card's `env(safe-area-inset-left|right)`). Symmetric centring needs no
flip; prefer `inset-x-0 mx-auto w-fit` over `left-1/2 -translate-x-1/2`.

**Guard.** `packages/web/__tests__/rtl-logical-classes.test.ts` scans every `.ts`/`.tsx` under
`components/` and `app/` (comments excluded) and fails with `file:line class` for a physical
class or inline style. Classes under `ltr:`, `rtl:` or a Radix `data-[side=left|right]:` variant
(the popper side is physical) pass. The few that must stay physical (the dialog's centring, the
pointer glows, the cookie card's phone insets, the switch thumb) are in its `ALLOWED` list with a
reason; an entry that no longer matches anything fails the test too.

**Icons.** An icon or arrow that means forward/back or "opens towards" mirrors with
`rtl:-scale-x-100`: `ArrowRight` on buttons, the dropdown submenu chevron, a collapsed
disclosure chevron, the reviews carousel arrows, and the stand-alone `→` spans in JSX
(`inline-block rtl:-scale-x-100`). Arrows inside catalog copy are flipped by the translators.
Clocks, refresh/rotate arrows, media play and external-link icons are not mirrored.

**Radix.** Radix primitives don't read `<html dir>`. `LocaleDirectionProvider`
(`components/DirectionProvider.tsx`, wrapping `@radix-ui/react-direction`'s `DirectionProvider`)
sits in the root layout and gives them the locale's direction: dropdown submenus open to the
left, arrow keys in menus and tabs follow the reading direction, and the scroll area puts its bar
on the left. Our own client code reads the same context with `useDirection()` (the reviews
carousel moves the track right and measures cards from the right edge; the password field keeps
the page direction). Tests set it by wrapping in Radix's `DirectionProvider dir="rtl"`. There must
be one copy of `@radix-ui/react-direction` in the install: it is a direct dependency at the
version the primitives use.

**Content keeps its own direction.** What users and web pages wrote is not in the page's
language, so it must not inherit the page's direction:

- Synced and shared data (group names, tab titles, notes, session and device names, store
  reviews): `dir="auto"` plus `text-start`, so an English title reads left to right inside an
  Arabic page and the other way round. Put `dir` on the element that truncates: the ellipsis is
  drawn at the end of that element's own direction. Padding that belongs to the page layout (an
  indent) goes on a wrapper without `dir`, or it flips with the text.
- URLs and domains: `dir="ltr"`.
- Inputs: `Input` defaults to `dir="auto"` for text and search, `dir="ltr"` for email, URL and
  phone (`inputDirection()` in `components/ui/input.tsx`); `Textarea` defaults to `dir="auto"`.
  A caller's `dir` wins. `PasswordInput` stays in the page direction, hidden or shown, because
  its reveal button and the padding kept for it are laid out in that direction.
- English-only pages (Privacy, Terms) are marked `lang="en"` and, under a right-to-left locale,
  `dir="ltr"`.
- Numbers built from separate pieces need an isolate of their own: the reviews strip's
  "4.28 / 5" (figure plus a "/ 5" span) and the pricing toggle's "−10%" are `dir="ltr"`, or a
  right-to-left page lays them out as "5 / 4.28" and "10%−". A price is one formatted string, so
  it needs nothing.
- Latin examples inside right-to-left copy go in a first-strong isolate (U+2068 … U+2069) in the
  catalog, one pair per Latin run, as the language search placeholder does with its example code "de".

**Language picker.** One button in the header at every width (the 2.25rem globe beside the theme
toggle below lg), never a second one in the mobile panel. Its menu has a search field (focused on
open, `filterLocales` from `@tabmerger/shared`: native, English and page-language names, codes,
aliases such as `iw` and `farsi`) above a list that scrolls inside a menu capped to the screen.
Each row shows the native name in its own direction, the name in the page's language
(`localeNameIn`), muted, and a fixed end slot with `PilcrowLeft` for a right-to-left language; a
screen reader hears "עברית, Hebrew, Right-to-left". The search field takes the page's direction
while empty, so its placeholder reads in it.

**Fonts.** Geist has no Arabic or Hebrew letters. `lib/fonts.ts` defines Noto Sans Arabic (Arabic
and Persian) and Noto Sans Hebrew with `next/font/google`, `preload: false`, all on
`--font-script`; `scriptFontClass(locale)` puts the matching class on `<body>` for those locales
only, and `--font-sans` in `globals.css` is Geist, then `var(--font-script, …)`. Latin words and
digits in an RTL page keep Geist; the script's letters come from Noto. Every visitor gets the
`@font-face` rules (a few hundred bytes), but a browser only downloads a face that rendered text
uses, inside its `unicode-range`, so left-to-right visitors download no script font. A new
right-to-left script (or any script Geist lacks) needs its own entry there. Nastaliq for a future
Urdu catalog would need extra line height: its ascenders and descenders are about twice Naskh's
and get clipped in `truncate` and fixed-height controls.

**Old language tags.** `negotiateLocale` (`i18n/negotiate.ts`) canonicalizes tags with
`Intl.getCanonicalLocales` before matching, so the legacy Hebrew `iw` (Android, older Java) reads
as `he`, and `in` as `id`, in `Accept-Language` and in the `NEXT_LOCALE` cookie. It only matters
once the canonical locale is supported. next-intl's own detection for the localized pages already
canonicalizes `Accept-Language` the same way (`@formatjs/intl-localematcher`).

**Previewing.** To see right-to-left layout without a catalog, add `'en-XA'` to `RTL_LOCALES`
locally and open `/en-XA/...` in `next dev`. Don't commit it: `rtl-direction.test.tsx` pins the
list.

## Extension

The popup, the extension pages and the background script (right-click menu, notifications, badge
titles) are translated. The store listing and the manifest `name`/`description` stay English (no
`_locales/`).

| Piece | File |
|---|---|
| Setup, `resolveLocale`, `t` for non-React code | `packages/extension/src/lib/i18n.ts` |
| Catalog registry | `packages/extension/src/locales/index.ts` (pages), `src/locales/worker.ts` (background worker) |
| Catalogs | `packages/extension/src/locales/<locale>/<area>.json`, listed in `<locale>/index.ts` |
| Typed keys (from English) | `packages/extension/src/i18next.d.ts` |
| Catalog checks | `packages/extension/src/locales/validate.ts`, `src/__tests__/unit/locales/catalogs.test.ts` |
| Pseudo-locale (dev builds, `build:dev:pseudo`) | `packages/extension/src/lib/pseudoLocale.ts` |

**Language.** The one picked in the popup header's language menu (applied at once) or in
Settings → General → Language (applied with "Save changes"); both show each language by its own
name (`LOCALE_NATIVE_NAMES` in `@tabmerger/shared`, which the web switcher uses too). "Browser
default", the default, is the browser's UI language (`chrome.i18n.getUILanguage()`), narrowed to a
shipped catalog: the exact tag, else its language (`de-AT` → `de`), else a shipped region of that
language (`pt-PT` → `pt-BR`, `zh-SG` → `zh-CN`), else English. Traditional Chinese (`zh-TW`,
`zh-HK`, `zh-MO`, `zh-Hant`) gets English, not Simplified. A key missing from a catalog shows
English.

The choice is per device and never synced (`src/lib/localePreference.ts`). It is stored twice:
in the extension origin's `localStorage` (`tabmerger-locale`), which extension pages read
synchronously so i18next starts in the right language with no flash, and in `chrome.storage.local`
(`tm_locale`) for the background worker, which has no `localStorage`. The worker applies the stored
choice on start, follows `storage.onChanged` and rebuilds the right-click menu; handlers that can
wake it (reminder notifications, sync-now replies, a new "Quick Save" group) wait for that first
read. Open extension pages follow the change too. Every stored value is validated with
`isSupportedLocale` and falls back to "Browser default". A change calls `i18n.changeLanguage` and
`applyDocumentLocale`, so `<html lang dir>`, dates, numbers and plurals follow.

**Writing translated code.** `const { t } = useTranslation()` in components and `<Trans>` for a
sentence with markup; `t` from `@/lib/i18n` in hooks and the background script. Interpolation is
i18next's `{{name}}`, not ICU. Counts use `t('common.tabCount', { count })`, which picks
`tabCount_one` / `tabCount_other` with `Intl.PluralRules`. Each language has its own plural forms:
Japanese and Chinese have only `_other`, Spanish, French and Portuguese add `_many`. The catalog
test checks every locale has exactly its language's forms, and the same keys, `{{placeholders}}`
and tags as English.

**Right-to-left.** `applyDocumentLocale` sets `<html dir>` from `i18n.dir()` (`rtl` for Arabic,
Hebrew and Persian), and the popup and the site-access page mirror from that one value:

- *Logical CSS.* The same rules as the web app: `ms-`/`me-`, `ps-`/`pe-`, `inset-s-`/`inset-e-`,
  `text-start`, `border-s`, `rounded-e`, `borderInlineStart` in inline styles. `rtl:` is for what
  has no logical form: the switch thumb's translate, and `rtl:-scale-x-100` on icons that point
  somewhere (Undo/Redo, the "Move to" arrow, collapsed and submenu chevrons). The sidebar's
  `borderInlineEnd` and the header's 240px logo cell stay one seam, now on the right. Positions
  computed in JS from `getBoundingClientRect` (tour rings, the drag ghost) stay physical: they are
  geometry. The guard is `src/__tests__/unit/styles/logicalDirection.test.ts`: it scans every
  `.tsx` under `src/` and fails with `file:line class` for a physical class or inline style key,
  except under `rtl:`/`ltr:`/`data-[side=…]` and its small `ALLOWED` list (the dialog's centring,
  the switch thumb).
- *Radix.* `LocaleDirectionProvider` (`src/components/LocaleDirectionProvider.tsx`) wraps each
  page's root in `@radix-ui/react-direction`'s `DirectionProvider` with the active language's
  direction, and re-renders on a language change, so menus, Select, Tabs and ScrollArea flip at
  once when the header's language menu is used. `useUiDirection()` reads it (the Toaster takes
  its `dir` and moves to the bottom-left corner).
- *Arrow keys.* Wherever ArrowLeft/ArrowRight move along a row, they follow the reading
  direction (`inlineArrow()` in `src/lib/direction.ts`): row controls (`useRovingRow`), keyboard
  move mode (towards the group list is ArrowRight in RTL, since the sidebar is on the right) and
  the tour (ArrowLeft is Next). Up/Down and Home/End are never flipped. The tour card's side, its
  docked corner and the drag ghost's grab point are mirrored too. Catalog copy that names a side
  or an arrow key ("the list on the left", "press the Left arrow key") is mirrored by the
  translators.
- *Content keeps its own direction.* Tab titles, group/window/session/device names, notes and
  search results render with `dir="auto"` on the element that truncates (so the ellipsis follows
  the text) and `text-ui-start` (`globals.css`: `left`, or `right` under `<html dir="rtl">`), so
  the line still starts at the UI's start edge. It reads `<html dir>`, never the parent:
  `match-parent` also copies a parent's `center` (a `<button>`'s default) and moved English text,
  and the guard test pins that. URLs, hostnames, URL-rule patterns, backup paths and email fields
  are `dir="ltr"`. Text inputs where names and notes are typed get `dir="auto"` only while they
  hold text (`dir={value ? 'auto' : undefined}`): Chromium treats an empty `dir="auto"` field as
  left to right, which lays a translated placeholder out backwards. Inline names in menus use
  `<bdi>`. Latin text inside right-to-left copy that must not reorder (the language search's
  "de, he" example) is wrapped in `⁦`…`⁩` (isolates) in the catalog.
- *Language pickers.* The header menu and the Settings row share `LanguagePicker`: a search box
  (`filterLocales` from `@tabmerger/shared`) over a listbox in a Radix Popover capped by
  `--radix-popover-content-available-height`. Rows show the native name (with its `lang`), the
  name in the UI language (`localeNameIn`) and, for `isRtlLocale` languages, a `PilcrowLeft` mark
  whose label is also in the accessible name.
- *Fonts.* Nothing is bundled: `html:lang(ar|fa|he)` in `globals.css` lists system fonts with
  those scripts (Segoe UI, SF Arabic/Hebrew, Geeza Pro, Arial Hebrew, Noto) before `system-ui`.
- *Old tags.* Chrome still reports Hebrew as `iw` on some platforms: `canonicalLanguageTag`
  (`src/lib/localePreference.ts`) reads `iw` as `he` and `in` as `id`, in `resolveLocale` and for
  a stored `tm_locale`/`tabmerger-locale` value, so they resolve once that catalog ships.

To look at RTL without a catalog, set `document.documentElement.dir = 'rtl'` in the popup's
DevTools: CSS, the keyboard and the tour follow it at once (Radix menus follow only a real
language change).

**Adding a language.** Copy `src/locales/en/` to `src/locales/<locale>/`, translate the values (and
adjust the plural keys to the language's forms), add the folder to `catalogs` in
`src/locales/index.ts` and its worker areas to `workerCatalogs` in `src/locales/worker.ts`, then add
the locale to `SUPPORTED_LOCALES`. That list is shared, so the web catalog must be complete first.

**Bundle size.** The popup and the background worker are separate bundles, so a catalog imported by
both ships twice. Pages load every catalog (`initI18n(catalogs, initReactI18next)`); the worker
loads English plus only the areas it reads (`WORKER_AREAS` in `src/locales/worker.ts`), and
`workerCatalogs.test.ts` fails when code the worker imports uses a key from another area. Page
builds are emitted as raw UTF-8 (`vite:build:extendConfig` in `wxt.config.ts`): WXT's default
`charset: "ascii"` writes each non-Latin character as a 6-byte `\uXXXX` escape. Scripts (the worker,
content scripts) keep ASCII, which content scripts need. With eighteen languages the unpacked
Chrome build measures about 3.88 MB. A Latin-script language adds roughly 90-145 KB; Arabic, Hebrew
and Persian take two bytes a letter and added about 190 KB each. CI's budget step (`ci.yml`, "Check
bundle size budget") fails above its limit, so check the headroom there before adding a language.
