name: share-bundle-pattern
description: Web dashboard sharing is fully client-side (lib/sharing.ts, no API route) — matches the extension; never reintroduce a server-side share/publish route
metadata:
  type: project
---

The dashboard's "Share" affordance (both the per-group `ShareButton` and the multi-select "Share selected" flow, both in `packages/web/components/dashboard/GroupGrid.tsx`) call `createSharedBundle()` from `packages/web/lib/sharing.ts` — a browser-only helper with no backing API route. As of 2026-09-26 there is **no** `/api/share-bundle` route; it was deleted.

**Why (history):** an earlier per-group "Publish" feature (`app/api/groups/[id]/publish/route.ts`) pointed the public `/share/[slug]` page at `groups.public_slug` directly, but `groups.windows` is ciphertext for every real account — that feature 404'd for everyone and was deleted outright. It was replaced by `POST /api/share-bundle`, which accepted client-decrypted `groups` in the request body and did the per-share key generation + encryption + `shared_bundles` insert *server-side*. That worked, but it meant plaintext tab content and the newly-generated decryption key both transited the network to the Next.js server on every share — never persisted, but momentarily present in server memory, which is a weaker guarantee than the extension's sharing path (`packages/extension/src/lib/sharing.ts`), which never leaves the browser at all. On 2026-09-26 the web route was deleted and replaced with `lib/sharing.ts`, mirroring the extension exactly: `generateDataKey()` + `encryptBlob()` + `exportKeyToBase64()` (all from `@tabmerger/shared`) run in the browser, and the `{v:1,iv,ct}` result is inserted into `shared_bundles` directly via the *browser* Supabase client (`lib/supabase/client.ts`), relying on the `shared_bundles_insert_owner` RLS policy (`supabase/migrations/009_create_shared_bundles.sql`) that already permits `auth.uid() = user_id` inserts — no service-role bypass needed.

**The correct pattern now:** any future "share this thing" feature should call `createSharedBundle(groups)` from `lib/sharing.ts` with an array of already-client-decrypted `{id, name, color, windows}` objects (even a single group) — not invent a new encrypt/store/link flow, and not route it through an API endpoint. If a route needs to touch `groups.windows`/`sessions.groups`/etc. server-side for some *other* feature, that's the `encrypted-column-auditor` bug class — accept client-decrypted plaintext in the request body instead, per CLAUDE.md's `organize` precedent (the only remaining example of that pattern; `share-bundle` is no longer a route to cite).

**Test-isolation gotcha (still applies):** when a test mocks `global.fetch` across multiple `it()` blocks in the same `describe`, an assertion failure mid-test can skip the `.mockRestore()` at the end of the test body, leaking mock call history into the next test. Add `afterEach(() => vi.restoreAllMocks())` to any describe block that mocks `global.fetch`, don't rely solely on an end-of-test `mockRestore()`.

**New gotcha from the 2026-09-26 migration:** testing a helper that calls `createBrowserClient`-backed `lib/supabase/client.ts` from a Vitest unit test needs `vi.mock('@/lib/supabase/client', () => ({ createClient: () => mockSupabase }))` — mocking `global.fetch` is a no-op verification (the point of moving to client-side sharing is that the mock target changes from HTTP to the Supabase client call). Vitest's jsdom environment provides `crypto.subtle` natively (Node 20+ webcrypto), so no crypto mocking is needed to test real `encryptBlob`/`decryptBlob` round-trips in these tests.
