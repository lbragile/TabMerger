---
name: supabase-env-import-crash
description: createClient('') throws at module-import time — the popup's whole entrypoint chain crashed in any env-less build/test run; fixed via placeholder .invalid host + isSupabaseConfigured flag
metadata:
  type: project
---

`src/lib/supabase.ts` called `createClient(supabaseUrl ?? '', ...)` at module scope. `@supabase/supabase-js@2.x`'s `createClient('')` **throws** (`Error: supabaseUrl is required`, via `validateSupabaseUrl`) — it does not degrade gracefully like the adjacent `console.warn` implied. Because `syncEngine.ts`, `deviceSessions.ts`, and `useEntitlements.ts` all import `supabase.ts` at module scope, and the popup pulls all three in transitively at startup, ANY build or test run missing `VITE_SUPABASE_URL`/`VITE_SUPABASE_PUBLISHABLE_KEY` crashed the entire popup at import time — not just "cloud sync disabled" as advertised. This was invisible in local dev only because `.env.local` always supplied real values; CI has none, so 37/136 unit test files failed to collect, all integration suites failed, and all extension E2E + visual regression tests failed (blank popup).

**Fix:** fall back to `https://supabase-not-configured.invalid` (RFC 2606-reserved TLD, guaranteed never to resolve — safe placeholder that can't accidentally hit a real endpoint) + a placeholder key, so `createClient` never throws. Added an exported `isSupabaseConfigured` boolean for callers that want to skip network calls proactively rather than let them fail via normal DNS/network error paths (which most callers already handle via try/catch or `{error} => return null`). Did NOT wire `isSupabaseConfigured` into every call site (syncEngine/deviceSessions/useSync) — `useSync.doSync` already gates on `session` truthiness first, and with no real Supabase reachable, `getSession()` returns no session, so the existing gate already prevents runaway calls in the main paths. Wiring it everywhere was judged out of scope/unnecessary risk for this fix; flag is there for future use if a caller needs a more explicit "sync unavailable" UI state.

**Test gotcha:** the existing `supabase.test.ts` mocks `@supabase/supabase-js`'s `createClient` entirely (to avoid spinning up multiple real `GoTrueClient` instances across its many `vi.resetModules()` reimports) — a mocked `createClient` can NEVER throw, so that file cannot catch this regression class. The real regression test needs its own file (`supabaseEnvDegradation.test.ts`) that does NOT mock `@supabase/supabase-js`, uses `vi.stubEnv` + `vi.resetModules()` + dynamic `import('@/lib/supabase')` to reproduce the real `createClient` call with env unset, and asserts no throw. Proved this test fails against the old code by `git stash`-ing the fix and re-running it in isolation before restoring.

**Repro recipe for "CI has no env vars" locally:** temporarily `mv .env.local .env.local.disabled` (also move any `.bak` copy out of the way, filenames don't need to exact-match `.env.local` to avoid Vite loading them, but keep the dir clean) and re-run `npx vitest run` — this genuinely reproduces CI's failure mode locally, rather than guessing. Vite/WXT's `loadEnv` loads `.env.local` for every mode including Vitest's default `test` mode, which is why the ambient dev env silently masks env-dependent bugs in local test runs.

**Related, separate flaky test found via the same repro:** `TabPreview.test.tsx`'s "only fetches the preview once across repeated opens (fetchedRef guard)" test didn't stub `VITE_WEB_APP_URL`, so it silently rode on whatever `.env.local` supplied. `getPageMetaForTab()` (`src/lib/tabAccess.ts`) short-circuits with no `fetch` call at all when `VITE_WEB_APP_URL` is falsy — so with no `.env.local` (CI), the test's `expect(fetch).toHaveBeenCalledTimes(1)` failed (0 calls), while locally it always passed. Not a real `fetchedRef` bug — fixed by adding an explicit `vi.stubEnv('VITE_WEB_APP_URL', 'https://tabmerger.app')` in that one test, matching the pattern already used by sibling tests later in the same file. Lesson: any test that asserts a `fetch` call count in this file needs its own explicit `VITE_WEB_APP_URL` stub — don't rely on the ambient default even if `beforeEach` calls `vi.unstubAllEnvs()` (that only reverts to whatever the *original* ambient value was, not to unset).

**The web package had the same pattern class:** `packages/web/lib/supabase/client.ts` and `server.ts` called `createClient(process.env.NEXT_PUBLIC_SUPABASE_URL!, ...)` with non-null assertions and no fallback. Both later got the same `.invalid` fallback fix (see web-dev's module-scope SDK construction note). When adding any new `createClient` call, use the fallback, not `!`.
