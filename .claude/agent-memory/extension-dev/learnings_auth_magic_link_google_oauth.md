- The web-app-to-extension session hand-off already exists and does NOT need `externally_connectable`/`onMessageExternal`. `packages/extension/src/entrypoints/content.ts` runs on the web app's own origin (matched via `VITE_WEB_APP_URL`), scans `localStorage` for a Supabase session (`access_token`/`refresh_token` keys), and forwards it via `chrome.runtime.sendMessage({ type: 'SYNC_AUTH', ... })`. `background.ts` already listens for `SYNC_AUTH` and calls `supabase.auth.setSession(...)`, which writes to `chrome.storage.local` under `tabmerger-auth`, and `useAuth.ts`'s `chrome.storage.onChanged` listener picks it up. So: magic-link sign-in just needs `signInWithOtp({ email, options: { emailRedirectTo: `${VITE_WEB_APP_URL}/api/auth/callback` } })` — no new bridge code required, the user finishes in a browser tab and the popup picks up the session next time it's opened.
- Google OAuth in an MV3 popup cannot use a plain redirect (popups have no navigation model). Use `chrome.identity.launchWebAuthFlow`: call `supabase.auth.signInWithOAuth({ provider: 'google', options: { redirectTo: chrome.identity.getRedirectURL(), skipBrowserRedirect: true } })` to get the authorize URL without navigating, then `chrome.identity.launchWebAuthFlow({ url, interactive: true }, cb)` to get the final redirect back to `https://<ext-id>.chromiumapp.org/`. Parse `?code=` from that URL and call `supabase.auth.exchangeCodeForSession(code)` (PKCE, the supabase-js v2 default flow) — with an implicit-flow fallback that reads `access_token`/`refresh_token` from the URL hash and calls `setSession()` directly. Requires `"identity"` permission added to `wxt.config.ts` manifest permissions.
- Found a pre-existing test in `useAuth.test.ts` (`'does not expose signInWithGoogle'`, comment: `// ponytail: runtime check that the removed method is gone`) indicating Google OAuth had been deliberately removed from the extension at some earlier point, with no memory/comment explaining why. When a later task explicitly asks to re-add a feature whose removal is guarded by a test like this, treat the new explicit request as authoritative — but flag the conflict to a maintainer, since the earlier removal may have had a reason (security review, incomplete OAuth client config, etc.) that isn't captured anywhere else.
