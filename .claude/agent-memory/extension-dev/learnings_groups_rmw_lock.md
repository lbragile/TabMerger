Technique notes for `lib/localDb.ts` (groups store writers):

- **`updateGroupsState(fn)`** is the read-modify-write primitive. `fn(current) => GroupsState | null` runs on a FRESH read taken inside the serialized write queue AND the cross-context lock; `null` skips the write; resolves with the resulting state. `fn` must be synchronous (no await, no chrome.* or network) and must never call `getGroupsState`/`saveGroupsState` (queue deadlock). Do network / chrome.* work BEFORE it and pass the results in via closure (see `syncNowOpen`, `performSync`).
- **`saveGroupsState` stays a blind overwrite** (prunes any stored group missing from the state). Valid only when the state is derived from the live cache in the same tick (DnD drop, undo/redo, import, demo seed). Anything that reads, awaits, then writes uses `updateGroupsState`.
- **One `enqueueGroupsWrite(task)` helper** bumps the gen synchronously, chains on the tail, and runs the task under `withGroupsLock`. `saveGroupsState`, `updateGroupsState`, `clearLocalAccountData`, `markAllGroupsPendingSync` all go through it, so a wipe can't be reordered against an earlier-issued write.
- **Raw reader for queued steps:** `readStoredGroupsState()` returns `null` for an empty store and never writes the initial group. `updateGroupsState` presents an empty store as `createInitialGroupsState()` instead of the read path's lazy init write. `readGroupsStateOnce` returns `null` (re-read) when it saw an empty DB but a write was issued since its start, so the first-run init can't clobber that write.
- **Cross-context lock:** `navigator.locks.request('tabmerger-groups-write', task)` (extension pages + MV3 SW share the origin; released automatically if the holder dies). Fallback when `navigator.locks` is absent (jsdom): a promise chain stored on `globalThis` under `Symbol.for(...)`, so even two `vi.resetModules()` copies in one test process exclude each other. Under fake-indexeddb the unlocked interleave is often masked, so the lock itself is proven by a unit test that stubs `navigator.locks` and asserts every writer requests it.
- **Telling other contexts:** `notifyGroupsChanged` now ALWAYS `sendMessage`s `TM_GROUPS_CHANGED` (after calling the in-SW direct listener). `chrome.runtime.sendMessage` never reaches the sender's own listeners, so it only hits foreign contexts. The popup's `useExternalGroupsChanges` listens and runs `invalidateQueries(GROUPS_QUERY_KEY, { cancelRefetch: false })`. The constant lives in `lib/groupsChangedMessage.ts` (test files that `vi.mock('@/lib/localDb')` can't supply it).
- **Merge inside the RMW:** `performSync` = push, fetch remote (network, outside the queue), resolve pending deletes, then one `updateGroupsState` that runs the pure `mergeRemoteGroups` against `fresh.available` and re-sorts by the CURRENT local order. `pullRemoteChanges` remains as the non-atomic snapshot variant (used by tests/legacy callers) built from the same helpers.

Test tooling gotchas:
- Hooks/libs that moved to `updateGroupsState` break every test that `vi.mock`s `@/lib/localDb` with only get/save. Use `withUpdateGroupsState({...})` from `src/__tests__/unit/_helpers/updateGroupsStateMock.ts` in the factory: `vi.mock('@/lib/localDb', async () => (await import('@/__tests__/unit/_helpers/updateGroupsStateMock')).withUpdateGroupsState({ ... }))`. It delegates to the object's own get/save mocks at call time. A mock whose `getGroupsState` returns the SAME object every call hides "mutated the first read in place" bugs (real reads return fresh objects) — keep migrations pure on the first read.
- Mounting a new hook in `App.tsx` requires mocking it in `App.test.tsx` / `appDndProvider.test.tsx` (they render with no QueryClient).
- Working-tree files are CRLF (autocrlf) while `grep -c $'\r'` in this shell reports 0: scripted edits must read, normalise to `\n`, match, then write back `\r\n`, or `git diff` shows the whole file changed. Use Edit for small changes. Heredocs containing unbalanced apostrophes break the Bash tool; write script files with Write instead.

Phase 3 additions (same module):
- **Durable pending remote deletes:** `writeGroupsState` adds every pruned (orphan) group id to the settings key `pendingDeleteGroupIds` and removes every id it (re)creates, inside the SAME transaction as the local write (tx now spans groups, groupsState, settings). `performSync` = push, re-send all pending DELETEs, fetch, then one `updateGroupsState(fn, { readPendingDeletes: true })` so the set is read inside the lock (`fn(current, { pendingDeletes })`). Ids leave the set only when a pull proves the row gone (`pendingBefore` minus all returned row ids, including encrypted-locked rows) or the server-side delete was the reason the local group was dropped. Wipes clear the key.
- **Version-checked sync flag:** `markGroupSynced(id, pushedUpdatedAt)` is a queued single-transaction step that only clears `pendingSync` when the stored `updatedAt` still equals the pushed one. A pending-only change that does not bump `updatedAt` (reorder) is not protected by it.
- **Sidebar order sync:** push `position` = index in `available` (Now Open 0, never pushed). Any index change marks `pendingSync` WITHOUT bumping `updatedAt` (`markReindexedPending`): a bump would let this device win LWW over another device's newer content. Pull adopts a remote `position` for groups with no unpushed local change, else keeps the local index; ties break by `updatedAt` desc then id.
- **Undo/redo as a local change:** `restoreSnapshotAsLocalChange(current, snapshot)` stamps fresh `updatedAt` + `pendingSync` on groups whose content differs (or are missing from current) and marks reindexed groups; same-content groups keep their current sync state.
- **Realtime LWW:** compare inside `updateGroupsState` before writing; the hook only refreshes the cache from IDB when the engine applied the update.
- Shell gotcha: the Bash tool rejects some heredocs/`node -e` bodies containing apostrophes; always create scripts and test files with Write.

Phase 4b additions:
- **`rev` optimistic concurrency:** the `groupsState` record carries a monotonic `rev`, bumped by every groups write and carried on `GroupsState.rev` through the cache. `saveGroupsState(state, { expectedRev })` rejects with `StaleGroupsError` (checked by `error.name`, so mocked localDb modules need no import) when the stored rev moved; it resolves with the new rev. The DnD commit passes its base rev and, if refused, re-runs `rebaseMove` + `applyMove` inside `updateGroupsState` on a fresh read (`redoDropOnFreshState`); if the drop no longer applies it throws into the existing rollback path. Undo/redo (`useSetGroupsState(state, { expectedRev })`) bails to a refetch. After a successful write the cache rev is patched forward only (`noteCacheRev`, never backwards).
- **Derived `positionDirty`:** `writeGroupsState` flags every non-permanent group whose index differs from the stored order (OR-ed with the stored flag so a blind cache-derived write cannot erase it). An incoming `positionDirty === false` is a caller's "already at this index on the server" claim for that one write only (used when a pull adopts the remote order); flags are normalised away before storing. Reorders push ONLY `update({ position })`; full-row pushes (fresh IV = content change) are never used for position.
- **Index-addressed mutators:** `alignToBase(base, fresh)` re-orders the fresh read to the list the user saw (by group id) so a positional index keeps meaning the same group; `null` (target gone) means "do nothing". Index-less mutators (`useAddGroup`, AI apply, shortcut save, import) pass `{ align: false }`.
- **Account scope:** `ensureAccountScope(userId)` memoises the last-user check/wipe per user so the sign-in effect and the first sync await the same wipe; `updateGroupsState(fn, { readSignedInUser })` lets `performSync` re-check the account inside the lock.
- Pending remote deletes: recorded only while cloud sync is active (`cloudSyncActive` setting), capped at 500, sent in chunks of 100, persisted exponential backoff after a failed cycle.

Round 3 additions:
- A "remote default" in a synced column (position 0) must be treated as UNKNOWN, never as a value: valid positions start at 1, and unknown-position rows are flagged so the next push fills them in.
- `restoreFreshOrder(fresh, aligned, result)` maps a mutation done on the base-ordered view back onto the fresh order (updates by id, drops removed, slots new groups after their predecessor, keeps the result order if the mutation itself reordered). A mutation whose target is gone resolves with `markAborted(state)`; `onSuccess` analytics check `wasAborted`.
- Undo that loses the rev race restores its history entry (`uiStore.restoreHistory`) and shows a stable-id toast; undo/redo history is dropped when foreign changes are applied (`onForeignGroupsChange`).
- Do not write a "flag" setting from a hook before its inputs (entitlements) are known; a default false clobbers the real value on every mount.

Round 4 (compare-and-swap "keep both" sync):
- Per-group `remoteUpdatedAt` = the SERVER `updated_at` last seen (pull/merge, applied realtime, every successful push via `.select('updated_at')`). Never compare it with the client `updatedAt`. Pushes: base -> `update(row).eq(id).eq(user).eq('updated_at', base).select('updated_at')` (zero rows = changed elsewhere, nothing written, group stays pending); no base -> `insert` (23505 = id collision). The push only guards; the merge resolves.
- Merge rules (pure `mergeRemoteGroups`): pending + stamp==base keep; pending + changed + equal content (`groupContentEqual`, sorted-key stringify because jsonb reorders keys) adopt; pending + changed + different content -> server copy wins, local edit becomes a pending "<name> (conflict copy)" (new id, no base) placed right after the original; pending + row gone + had a base -> same copy with the original id dropped; locked rows never resolved. Idempotent because the original stops being pending in the same atomic RMW.
- Legacy vs new: no base is legacy until the first sync after the upgrade finishes (`remoteBaseSeeded` setting): during that window a pending group probes its row (`select('updated_at').maybeSingle()`) and adopts the stamp as its base, so an upgrade never makes copies.
- A position-only update bumps updated_at on servers without migration 020, so it must be guarded by the same base and store the stamp it gets back, otherwise the device conflicts with itself. Blind `saveGroupsState` preserves the STORED base (`preserveBases`) so a stale cache cannot regress it.
- syncEngine must not import the toast (it also runs in the service worker): it emits `emitSyncConflict(names)` and `useSync` shows the toast with id `sync-conflict-copy`.

Round 5 (third audit pass):
- **New identity = no sync identity.** `remoteUpdatedAt` / `positionDirty` belong to ONE server row. Anything that copies a group under another id (duplicate, import, undone delete whose row may be gone) must strip them (`asNewGroup`, `restoreSnapshotAsLocalChange`'s `!cur` branch, `prepareImportedState`); otherwise the push is a compare-and-swap on a missing row and the merge turns it into a "(conflict copy)". Imports (replace and append) also regenerate ids so a backup made on this account cannot collide with its own rows.
- **Stamps are instants**: `lib/stamp.ts` (`compareStamps`/`sameStamp`) parses `T`/space, `Z`/`+00:00`/`+00`, any fraction length into integer microseconds (Date would lose them). Only COMPARE through it; always SEND the raw stored string to `.eq('updated_at', …)`. Adopt a remote row only if its stamp is NEWER than the base (an overlapping cycle's older snapshot must not replace newer local data).
- **One sync cycle at a time**: `withSyncLock` (Web Lock `tabmerger-sync`, `ifAvailable`, globalThis flag fallback) around the whole cycle; a skipped call returns local state.
- `markGroupSynced` compares updatedAt AND content: two edits inside one millisecond share an updatedAt (this was the cause of the flaky "edit in flight" test).
- `remoteBaseSeeded` is set only when no pending no-base group with a (locked) remote row remains; the pull is paginated by keyset on `id` (`.gt('id', last).order('id').limit(1000)`, any failed page aborts the cycle; see [[learnings-encryption-key-tristate]]).
- Undo/redo history is cleared on account wipe, sign-out and Settings "Clear all data".
- Test infra: `vitest.integration.config.ts` now has two projects: `fake` (parallel) and `real` (3 real-network suites, `fileParallelism: false`). Run the real ones with `--project real` and the env from the test-writer note (after resetting the local test users' passwords through the admin API a first realtime test can time out once; a rerun passed).
