Implemented the Firefox BETA build's manifest pieces: `gecko.update_url`, `data_collection_permissions`, and a Firefox-safe version badge fallback.

- WXT's `manifest` config accepts a fn `({ mode, browser }) => UserManifest` — `ConfigEnv.browser` (`TargetBrowser`, from `-b`/`--browser`, defaults `"chrome"`) is there for free alongside `mode`, no need to parse `process.argv` yourself the way `zip`'s static config already does elsewhere in this file.
- WXT's own bundled types (`wxt/dist/types.d.mts`) already export `FirefoxDataCollectionPermissions`/`FirefoxDataCollectionType` — `browser_specific_settings.gecko.data_collection_permissions` is a first-class typed manifest field, not something to hand-roll as `Record<string, unknown>`.
- Current AMO `data_collection_permissions` schema (verified via a research subagent against extensionworkshop.com's "Firefox Built-in Data Collection Consent" page, 2026-09-27): `{ required: string[], optional?: string[] }`. Category strings are camelCase (`personallyIdentifyingInfo`, `healthInfo`, `authenticationInfo`, `websiteContent`, `technicalAndInteraction`, etc. — no `_data`/`_info` snake_case). `"none"` is only valid in `required`, and only alone there. `technicalAndInteraction` can ONLY go in `optional`, never `required` — even though this repo's analytics (`src/lib/analytics.ts`) fires by default with no toggle, that doesn't make it "required" in AMO's sense; "required" means "needed for the extension's core functionality," which TabMerger's free/offline tier doesn't need any of. Required for new AMO submissions since 2026-09-27, with an unspecified grace period for pre-existing add-ons — check the Mozilla Add-ons blog post directly if the exact grandfather deadline ever matters.
- A manifest-build test asserting Firefox beta's `update_url` should NOT hardcode `.env.beta`'s `VITE_WEB_APP_URL` value — a local `.env.local` legitimately outranks it under Vite's `loadEnv` precedence (`.env.local` > `.env.<mode>`), so the real build-output test must assert the URL *shape* (regex) rather than the literal `.env.beta` value, or it fails on any machine with a `.env.local` override (which this repo's local dev setup always has).
- Extracted the update_url resolution (with its "throw if VITE_WEB_APP_URL is unset" guard) into a standalone `scripts/firefoxBetaUpdateUrl.ts` purely so it's unit-testable without a real `wxt build` — `wxt.config.ts` itself can't be unit-tested directly, only asserted on via real builds (`test:manifest`, slow: ~2.5 min for 9 cases).
- Firefox drops the Chrome-only `version_name` manifest field entirely (not schema-validated, just not part of the WebExtensions spec) — `chrome.runtime.getManifest().version_name` reads `undefined` there even though the built `manifest.json` file itself still contains the key. Fixed the Settings badge by injecting `__TABMERGER_VERSION__` via a Vite `define` (declared as a global in `src/env.d.ts`, mirrored in `vitest.config.ts` as `'0.0.0-test'` for tests) and falling back to it only when `navigator.userAgent` matches `/firefox/i` — narrower than an unconditional `version_name ?? __TABMERGER_VERSION__ ?? version` chain, which would have broken the pre-existing "falls back to version" Chrome unit test (whose mock `getManifest()` return value is unrelated to the real build's injected define).
