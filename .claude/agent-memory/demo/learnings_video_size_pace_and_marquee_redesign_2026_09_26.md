## Headless `recordVideo` ignores `deviceScaleFactor` COMPLETELY — a new, different quirk from the old headed one

`record.ts` had a long-standing comment (2026-08-01) that headed `recordVideo` captured at an effective ~1.25x scale (1000x750 for an 800x600 viewport) *regardless* of `deviceScaleFactor`, and hardcoded `recordVideo.size` to `{1000,750}` to match. After this session's switch to headless-by-default, a review caught the popup only filling ~640x480 (top-left) of the 800x600 render canvas with gray padding right/below — i.e. the OLD fix was now wrong. Measured directly (extracted a raw frame via ffmpeg, inspected the actual content boundary): under `--headless=new`, `recordVideo` captures the RAW CSS viewport size (800x600) with **zero scaling from `deviceScaleFactor` at all** — not 1.25x, not 2x, exactly 1x — while `page.screenshot()` in the same context still honors DSF correctly. **Lesson: a documented workaround tuned for one browser mode (headed) can become the exact bug in a different mode (headless) — when switching modes, re-measure every "known quirk" empirically instead of assuming the old tuned constant still applies.** Fixed by setting `recordVideo.size` to `{800,600}` (matching what headless actually produces) instead of `{1000,750}`. Kept `deviceScaleFactor:2` in the launch call anyway since it's a genuine (if partial) no-op for video now — `page.screenshot()` calls elsewhere in the same context still benefit.

## `playbackRate` on `OffthreadVideo` is the correct tool for "make it faster without cutting it off"

Decision: both the promo (was 82.9s) and walkthrough (was 103.1s) must hit **hard** caps (30s / 60s) — shortening `durationMs` per step was explicitly the wrong move (demo-script.ts's own convention: `durationMs` is a hard *playback* cap on already-trimmed real footage; cutting it shorter than the recorded action freezes mid-motion, which reads as broken). The actual fix: keep every step's `durationMs` (i.e. the amount of REAL source content) unchanged, but render it back faster. Added a `speed` prop to `WalkthroughDemo`/`getTotalDurationInFrames` (both MUST apply the identical math or the `<Composition durationInFrames>` Root.tsx passes drifts from what the component actually lays out, which either truncates the real last beat or renders trailing blank frames) that:
- shrinks the on-screen `Sequence` duration to `nominalFrames / speed` (with a `Math.max(45, ...)` floor = 1.5s, so a caption is never on screen for less time than a viewer needs to read it — never actually the binding constraint here, all beats cleared it with margin), and
- passes `playbackRate={speed}` to `OffthreadVideo`.
Net effect: `outputDuration * playbackRate == originalDuration` — the ENTIRE original recorded action still plays, just compressed in on-screen time (sped-up motion), never truncated. Solved the exact `speed` constant algebraically per composition (`action-beats-total / speed + fixed-intro-and-text-card-time <= target`), not by trial and error — `remotion compositions` (fast, no render) confirms the resulting total duration immediately without a full render pass, useful for iterating on the constant before committing to an expensive re-record+re-render.

For the promo cut specifically, hitting 30s also required actually DROPPING most beats (keeping this priority list: chaos → organized, multi-select drag, cross-group drag, closing card) rather than relying on speed alone — going from 11 beats to 4 + outro, THEN applying a modest 1.3x speed, rather than one enormous speed factor on all 11 (which would have made individual actions unreadably fast). **Lesson: for a large duration cut, cut beats first, then speed up what's left — a single huge speed multiplier on everything reads as frantic, a moderate speed multiplier on a curated shorter list reads as "fast-paced" the way the ask intended.**

## Zoom removal (decision: if in doubt, remove the zoom)

Removed the whole `ZoomVideo` component and its call site in `Composition.tsx` — every step now renders a plain `OffthreadVideo` regardless of its `zoom` field (left inert in `demo-script.ts`/`zoom-origins.json` rather than deleted everywhere, in case a future re-introduction wants it for one beat where the full action verifiably stays in-frame). The zoom's actual failure mode wasn't cosmetic: it was hiding the ends of drag beats (the crop excluded either the drop target or part of the cursor path for the beats it was most applied to), which is a real usability bug for a promo video about drag-and-drop specifically — worth remembering as the concrete reason "if in doubt, remove it" is the right default for this kind of effect, not just a style preference.

## `PromoTile`'s "many tiny tabs, sane scale" fix: this was never an `objectFit` problem

Two prior passes this session tried `contain` (round 1: technically uncropped but near-invisible + huge empty space) then `cover` at an oversized height (round 2: filled the box but cropped to ~1-2 tabs blown up 3.5-12x) for the same wide/short (9:1) cluttered-chrome capture. **Both were the same root mistake**: forcing a 9:1 image to fill a ~1.1:1 box's HEIGHT is fundamentally a choice between "width-limited scale, huge empty space" (`contain`) and "height-limited scale, crop most of the width away" (`cover`) — there is no third `objectFit` value that avoids both. The actual fix doesn't touch `objectFit` at all: stop requiring full-height fill. Size the image to the panel's WIDTH at its natural, undistorted aspect ratio (`width:100%`, `height:auto`, no `objectFit` needed since nothing needs cropping — every tab stays visible, uncropped, at a legible ~1.5x-of-native scale for this panel width), and use `display:flex; alignItems:center; justifyContent:center` on the panel to place the resulting short strip in the vertical middle. The panel's own dark background above/below then reads as a deliberate "browser mockup on a card" framing (a normal promo-tile pattern), not as the "half the panel is dead black" bug from round 1 — because the panel itself was already correctly bounded (`calc(100% - banner)`, from an earlier fix pass) and the image only occupies a modest fraction of it now, not most of it. **Lesson: if two opposite `objectFit` values both produce a complaint, the box's sizing requirement itself is probably wrong, not the fit mode** — stop tweaking the fit property and question whether the element needs to fill that dimension at all.

## `screenshots.ts`'s headless-reuse gate must back up the file BEFORE the directory wipe

Implementing "skip the one capture that needs a real window by default, reuse the existing file" is trivial to get backwards: `main()` unconditionally `fs.rmSync(RAW_DIR, {recursive:true, force:true})`s at the very start (to clear stale PNGs from renamed/removed steps) — if you check "does cluttered-chrome.png exist" AFTER that wipe, it never does, and the whole feature silently does nothing every run. Read the existing file into a `Buffer` first, wipe, then either recapture (opt-in, `TM_DEMO_HEADED=1`) or write the buffered copy back. Verified end-to-end: a plain headless run now logs `reused existing .../cluttered-chrome.png` and launches zero extra Chrome processes for this step.
