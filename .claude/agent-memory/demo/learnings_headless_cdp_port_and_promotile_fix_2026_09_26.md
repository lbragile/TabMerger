Direct follow-up to [DnD rebuild + headless + new multi-select/cross-group beats](learnings_dnd_rebuild_headless_and_new_beats_2026_09_26.md) — that pass documented headless drag as a "genuine Chromium limitation" and recommended porting to raw CDP as future work. This session did that port. It fixed it completely.

## Raw CDP `Input.dispatchMouseEvent` fixes headless drag — `page.mouse` does not, despite calling the identical CDP method

Confirmed via a minimal standalone repro (drive one drag via `context.newCDPSession(page).send("Input.dispatchMouseEvent", ...)` instead of `page.mouse.*`, same coordinates, same headless launch): `document.body.style.cursor` flips to `"grabbing"` (proof the popup's `dndHtml5Sensor.ts` activated) under `--headless=new`, where the equivalent `page.mouse.move/down/up` sequence produced nothing. Both APIs ultimately call the same CDP `Input.dispatchMouseEvent` — the difference is almost certainly Playwright's own mouse-state bookkeeping/event batching (multiple logical moves coalesced, or extra fields set) versus a bare, one-event-per-call dispatch. **Lesson: don't assume "same CDP method under the hood" means "same behavior" — a raw, minimal dispatch can behave differently from a high-level wrapper's dispatch of the identical primitive, especially for anything gated on discrete native browser heuristics (native drag detection here).** Ported by adding a `CdpMouse` class (`lib/actions.ts`) that mirrors `page.mouse`'s `move/down/up` shape (tracking its own last x/y, since `Input.dispatchMouseEvent` needs explicit coordinates every call) — this meant `naturalMouseMove` and all 5 drag actions only needed their `page.mouse.*` calls swapped for `mouse.*`, no restructuring. One `CDPSession` per `Page`, cached in a `WeakMap`, reused across a step's several drag calls.

After the port: both themes record and the four videos render **fully headless with zero relaunch/retry crashes** — previously every run needed `TM_DEMO_HEADED=1` and even then had occasional crash-retries.

**Still headed, unavoidably**: `screenshots.ts`'s `captureClutteredChrome()` uses OS-level `PrintWindow` to capture the real native Chrome tab strip/bookmarks bar for the promo marquee's "chaos" panel — `page.screenshot()`/CDP fundamentally cannot see native browser chrome, headless or not, and there's no real HWND to `PrintWindow` in headless mode anyway. This is a different problem class from the drag fix above and has no headless equivalent; documented as the one legitimate exception in README.md.

## `chaosHook`'s real external site navigation is an ongoing, unpredictable "AI text" risk

`chaosHook` (and `captureClutteredChrome`) deliberately navigate to REAL live external sites (not mocked data) so the "chaos" reads as authentic. This means the tab titles shown in "Now Open" are whatever that site's live `<title>` happens to be AT RECORDING TIME — not anything hardcoded in this repo. Found when a rendered frame showed "Gmail: Secure, AI-Powered Email for…" and "The AI workspace that works for you…"): these came from `https://mail.google.com/...` and `https://www.notion.so` in `CHAOS_WINDOW_SETS` (`lib/actions.ts`) — NOT from `packages/extension/src/lib/demoData.ts` (that data is static hardcoded strings, verified clean, no edit needed — an extension-dev delegation for this turned out to be a misdirected ask). Also caught `https://www.figma.com` mid-session (its real title now includes "...and AI"). **Any real external URL used anywhere in this pipeline can start mentioning "AI" (or anything else undesirable) at any time, with zero warning, because it's someone else's live marketing copy.** Before adding/keeping a live external URL in `CHAOS_WINDOW_SETS`, `NOW_OPEN_SEED_URLS`, or `captureClutteredChrome`'s `tabUrls`, verify its current live `<title>` first: `curl -sL <url> | grep -io "<title>[^<]*</title>"`. Swapped to Yahoo Mail (`mail.yahoo.com`) and Dropbox (`dropbox.com`) for the email/workspace slots, and Sketch (`sketch.com`) for the design-tool slot — all verified clean at swap time, none guaranteed to stay that way forever; re-verify at the same time as any future demo refresh, don't just trust a comment saying "checked once."

## PromoTile.tsx layout math for oddly-shaped source images

Two real CSS bugs in `remotion/stills/PromoTile.tsx`'s `MarqueeTile`, both root-caused by treating every image box as "the same height as the whole tile":

1. `captureClutteredChrome()`'s output is an inherently WIDE/SHORT crop (1400×155, a chrome-band-only capture) — `objectFit:"contain"` in a box that's the FULL tile height sizes the image by the width-limited scale (the only way `contain` can fit a 9:1 image into a ~1.1:1 box), producing a tiny ~68px-tall sliver dead-centered with huge empty space above/below. This is `contain`'s correct, expected behavior for an image this disproportionate to its box — not a rendering glitch. Fixed with `objectFit:"cover"` instead (fills the box, crops left/right).
2. Even after switching to `cover`, a plain height:100% cover box revealed a second problem: the *source* capture's bottom edge includes a thin sliver of the real (white) page content peeking out below the bookmarks bar (invisible at the image's native tiny scale, hugely magnified once `cover` scales the whole band up ~3.5-12x to fill a much taller box). **The fix is NOT `objectPosition` or a negative `top`** (tried first, wasted several iterations — a negative `top` shifts the crop window DOWN into the image, revealing MORE of the bottom, i.e. exactly backwards from "hide the bottom sliver"). The fix is `top:0` + an explicit `height` LARGER than the container (e.g. `height:640` in a `444`-tall, `overflow:hidden` box) — this anchors the scaled image at the container's top edge and lets only the excess BOTTOM portion overflow into the clipped area. Both boxes (chaos panel AND the organized-screenshot panel) also needed their height changed from `100%` to `calc(100% - BANNER_HEIGHT)` so neither image box can structurally reach into the bottom text-banner's pixels at all — the original bug (headline text overlapping the popup's own footer row in the screenshot) was two DOM boxes genuinely occupying the same pixels, not a z-index/opacity issue a gradient could hide.

**Debugging dead-end worth flagging**: while iterating on this, several style edits (percentage-based `top`/`height`, e.g. `top:"-45%", height:"180%"`) produced BYTE-IDENTICAL `remotion still` output across multiple edits — looked exactly like a caching bug (confirmed via `certutil -hashfile` that outputs actually DID differ in bytes despite looking visually identical, and separately found `%LOCALAPPDATA%\Temp\remotion-webpack-bundle-<hash>` — see below) but was ACTUALLY just the wrong fix direction (negative-top moves the crop the wrong way) combined with a percentage-height magnitude too small to visibly matter at typical viewing zoom. Don't assume "identical output after an edit" always means a cache bug — try a deliberately EXTREME value first (e.g. `top:-1600` instead of `top:-45%`) to immediately confirm the edit is even taking effect and in which direction, before hunting for a caching explanation.

## Remotion's `remotion-webpack-bundle-<hash>` temp dir can serve a stale bundle

Found `%LOCALAPPDATA%\Temp\remotion-webpack-bundle-<hash>` (a FIXED-name dir, not re-hashed per run) alongside several `remotion-v<version>-assets<random>` dirs. When debugging why edits seemed to have zero effect (see above — they didn't, but this is still real and worth knowing), deleting `node_modules/.cache` alone did NOT force a rebundle; deleting the `remotion-webpack-bundle-*` dir did force a real "Bundling 6%...100%" pass on the next `remotion still`/`render` call. If a Remotion composition ever appears to ignore a source edit, delete `%LOCALAPPDATA%\Temp\remotion-webpack-bundle-*` (Windows) before concluding the change didn't apply.
